## Impact and limits

- The existing Next.js 14.2.35 critical finding applies to the application framework, including server rendering/request handling. Editor restoration does not repair those framework findings. Exploitability depends on hosting and feature configuration; no exploit or target deployment verification was performed. Treat framework remediation as a separately coordinated release decision.
- PostCSS, nanoid, selector-parser, glob/pattern expansion, Browserslist and lint-chain findings are pre-existing. Build tooling and any runtime CSS transformation must be distinguished before assessing exposure. The new editor adds react-email as a transitive dependency and therefore additional code/tooling; no finding specifically names @react-email/editor, sanitize-html, Tiptap or ProseMirror in the saved candidate report. This does not prove absence of vulnerabilities or remove risks from shared dependencies.
- The application loads the editor dynamically with SSR disabled. Server email bodies use allowlisted sanitize-html processing. It does not call the react-email development server/CLI for these email sends. This limits relevance of editor tooling to this send path, but is not a blanket server-safety claim.
- Existing form-data, Google API/uuid, exceljs/uuid and js-cookie findings remain in the dependency graph; no new use of those APIs was added by this feature. Individual advisory preconditions have not been exhaustively verified.
- Target-schema review, authenticated per-surface UI verification, deletion UI verification, and authorized inbox rendering tests remain release gates. No real-recipient tests or production actions were performed.
