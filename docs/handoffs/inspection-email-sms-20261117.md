## Requested behavior

The user requested an SMS alongside the initial client site-visit request/invitation and the later inspection with the purchasing cleaner. They explicitly selected the client inspection invitation email as the second trigger, rather than sale completion.

After the email provider accepts the client email, save a private receipt and enqueue one SMS through the existing SMS worker:

1. Public, CRM and partner booking email: pending request or confirmed visit wording, matching that email's status.
2. Partner alternative-time request and subsequent confirmation: one notice per stage. Declines do not create SMS.
3. Product-sale inspection invitation: client only, using the CRM client's mobile. No cleaner/staff SMS and no sale-completion trigger.

The SMS directs the client to their email/junk folder. Pending requests explicitly say the time is unconfirmed. Each fixed message is one GSM segment and includes STOP instructions. No internal notes, appointment address or purchasing details are copied into the SMS.

Receipts are unique per appointment snapshot and request/confirmation kind. Email resends do not add SMS. Changes to the appointment, recipient, cancellation, decline or passed appointment block queued delivery. Product-sale inspection notifications are independent of accepted-quote status. Existing STOP, email-only, disabled automation, quiet hours, provider reconciliation, frozen payload and owner alert handling remain in place. No global marketing consent is created.

If receipt storage fails after email acceptance, the email remains accepted and an SMS alert is recorded; the email is never resent by this helper. This is a review path, not an automatic email replay.

## Migration, API and rollout

Apply `20261116231302_inspection_email_sms.sql` before deploying the app, once release is authorized. Filename was generated by Supabase CLI (16 November UTC / 17 November Melbourne). It creates private `sms_inspection_emails`, adds nullable `sms_jobs.inspection_email_id` with a unique partial index, adds three service-only functions, and narrowly extends existing `sms_dispatch` eligibility/cooldown handling. RLS and grants are tested: receipt rows are unavailable to anonymous/authenticated roles; service role has SELECT/INSERT only. No backfill, settings update, customer-record change, send or enqueue is performed by applying the migration alone.

New service-only RPC: `sms_record_inspection_email(p_entity_type, p_entity_ref, p_kind, p_phone, p_recipient, p_snapshot, p_provider_message_id) -> boolean`. It checks the stored booking/client snapshot and destination. Helper functions read current appointment context and reject stale jobs at dispatch. Existing API contracts remain compatible; the owner SMS history response only gains fields.

Read-only production checks on 17 November found `auto_enabled=true`, delay 5 minutes, maximum 2 segments and provider health ready. These settings are not changed. Therefore, once deployed, future eligible client inspection emails will automatically schedule SMS after the current five-minute delay, subject to the existing Monday-Friday 9am-6pm client-local sending hours and worker scheduling. No old emails are backfilled. Turning automation off continues to cancel pending automatic jobs.

## Remaining release work and limitations

- Wait for a user release request; then coordinator reviews/applies migration, integrates this patch, validates combined changes and verifies the actual live commit.
- A live SMS/email delivery test requires separate explicit authorization and an agreed test recipient. No real send has been performed for this feature.
- Invalid/non-mobile numbers are skipped and flagged. SMS acceptance/delivery remains asynchronous and subject to existing provider health, credit and quiet-hour rules.
- A crash between provider email acceptance and receipt persistence cannot be made atomic across providers. The existing email workflow's review behavior remains; normal helper failures record an SMS alert and never resend the accepted email automatically.
- Rollback of the application can leave this additive schema in place; there is no destructive rollback or historical backfill.
