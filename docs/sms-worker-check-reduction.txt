Account/sender/webhook checks reuse the existing persisted healthy diagnostic
for less than five minutes on idle runs. The next worker tick at or after five
minutes refreshes it (nominally five minutes; scheduler jitter can add a tick).
Missing, failed, invalid or future-dated diagnostics refresh immediately.
Every run with claimed outbound jobs performs a fresh full provider check before
processing those jobs, even if the idle diagnostic is recent. Failures prevent
dispatch; claimed jobs retain existing expiring leases for recovery.
No credential or configuration fingerprint is added to persisted health.

Cron remains every minute. Inbound history recovery with its one-day overlap,
STOP suppression sync, submitted-message reconciliation eligibility (one hour),
24-hour overdue alerts, heartbeat and stale-worker alerts are unchanged. Empty
outbound queues do not short-circuit recovery. Cached healthy diagnostics can
delay discovering idle provider configuration or balance changes by about five
minutes, but outbound processing still requires fresh readiness and balance.

Health and completed inbound checkpoints are saved together with the existing
token-guarded worker lease release. The heartbeat remains at worker start.
A normal completed live run now makes three settings writes including the lock
RPC, instead of five: lock, heartbeat, release. This removes two SQL updates per
normal run without changing the schema. If the process dies before release,
the checkpoint remains old and recovery replays through existing event deduping.
The settings release still reports database errors.

For an entirely idle healthy hour, nominal full configuration checks fall from
60 to 12 (180 to 36 provider GET requests). Actual cadence depends on scheduler
timing, errors and outbound jobs. This does not remove cron dispatches or prove
any reduction in measured database I/O; cumulative statement time was not I/O.
